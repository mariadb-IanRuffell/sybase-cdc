# Sybase + Oracle → GridGain: phased migration PoC (data hub)

Two source systems with deliberately **different, complementary data** are moved onto one GridGain 9.2 cluster in the same
two phases, and joined there:

| System | Domain | Data | Join key |
|---|---|---|---|
| **Sybase ASE** (on `llama`) | CRM / commerce: "customer 360" | customers, addresses, products, orders, payments, loyalty, interactions | `customer_id` |
| **Oracle 26ai Free** (local Docker) | travel / reservations | airports, flights, seat inventory, bookings, segments, flight events, compensation | `booking.customer_id` = the Sybase customer id |

```
Sybase ASE ──triggers──► change log ──► CDC reader ─┐                          ┌─► compute jobs (the former stored procedures)
                                                    ├─► GridGain 3-node cluster ┼─► REST API (CRUD + operations + hub) + live dashboard
Oracle ─────triggers──► change log ──► CDC reader ─┘   (native persistence)    └─► cross-source SQL joins (hub/queries.sql)
```

| Phase | Goal | Status |
|-------|------|--------|
| 1 | CDC from each source into GridGain (the sources stay systems of record) | **done** for Sybase and Oracle |
| 2 | Re-implement each source's stored procedures as GridGain compute jobs; apps call GridGain | **done** for Sybase and Oracle (plus a REST API in front of both, and hub jobs that join them) |

There is no third phase: decommissioning is just switching Sybase and the CDC reader off. That needs the applications to stop writing in Sybase and GridGain to be the only durable copy; see "Before switching Sybase off" below.

### Stored procedures and what each demonstrates for the compute-job migration

| Procedure | Pattern | Likely GridGain shape |
|-----------|---------|-----------------------|

## Phase 1 (done): trigger-based CDC into GridGain 9.2.0-b1

```
Sybase ASE --triggers--> cdc_change_log --poll--> cdc/ (Java) --upsert/DELETE--> GridGain (thin client + JDBC)
```

- **Sybase side** (`sybase/sql/04_cdc.sql`, generated by `generate_cdc.py`): `cdc_change_log`
  (table, op I/U/D, pk), `cdc_offset` (consumer checkpoint), and one trigger per table.
  Triggers log only the key, so the log stays narrow and the sources need no schema change.
- **Reader** (`cdc/`): batches log rows, collapses them to distinct keys, re-reads the *current* row from
  Sybase and upserts it into GridGain through the key-value API (GridGain 9 SQL has no single-row upsert; the values are converted to the column types), or DELETEs it if the row is gone. Because it applies state rather than
  operations, replays are harmless; the offset is committed only after GridGain has the data.
- **GridGain** (3-node persistent cluster, see "GridGain cluster" below; image `gridgain/gridgain9:9.2.0-b1`, native arm64):
  tables from `cdc/src/main/resources/gridgain-schema-sybase.sql`, created in distribution zones. Customer-owned tables are
  `COLOCATE BY (customer_id)` in zone `c360` (3 replicas); `order_item`/`payment` carry a denormalised `customer_id` (resolved through
  `orders`); `product` and `loyalty_tier_rule` are in zone `c360_ref`, which keeps a copy on every node. This is the layout the compute jobs use.

```bash
cd gridgain && ./cluster.sh up               # 3-node persistent GridGain 9 on :11800/11801/11802
cd ../sybase && ./deploy.sh                  # (re)build Sybase schema, seed, procs, CDC triggers
cd ../cdc
./run.sh init      # create GridGain tables, snapshot copy, set offset to the pre-copy watermark
./run.sh run       # stream continuously from the host (CDC_POLL_MS, CDC_BATCH env vars); normally the
                   # gg-cdc container does this, see below. Never run both at once.
./run.sh once      # apply one batch and exit
./run.sh status    # offset, pending events, row counts on both sides
./run.sh verify    # compare every column of every row; exit 1 on any difference
```

Verified: after `init` all 10 tables are row-for-row identical; live changes from stored procedures
(order flow, bulk scoring) and direct DML (insert, update, multi-row delete) converge within seconds;
changes made while the reader was stopped are applied on restart.

**Known limits (PoC):**
- Ordering relies on ASE blocking readers behind uncommitted log rows (default locking), so a long open
  transaction delays CDC rather than being skipped. Large production use would want datarows locking and a
  commit-aware cursor, or a log-based tool.
- Deletes from GridGain use `WHERE pk = ?` (a scan for composite-key tables); fine at this size.
- Sybase datetimes are treated as UTC; the reader JVM runs with `-Duser.timezone=UTC` to match the
  GridGain node. Without it, summer-time rows were off by one hour (caught by `verify`).
- Writes to GridGain are not transactional across tables, so readers may briefly see a partial batch.
- `cdc_change_log` is never purged; add a retention job before running this for long.

## Phase 2 (done): stored procedures as GridGain compute jobs

All six procedures now exist as Java compute jobs in `phase2/`, deployed to the cluster as one deployment unit (`customer360-jobs`) and
called by name through the thin client (no cluster membership needed from the caller). A job takes a JSON object and returns JSON (strings
travel natively, and nested maps and lists need no extra serialiser in the unit); per-customer jobs run on the node that holds the customer's
partition (`JobTarget.colocated`), the others on any node.

| Sybase procedure | GridGain job | How it changed |
|---|---|---|
| `sp_customer_360` | `Customer360Job` | Runs on the node owning the customer's partition; same 6 result sets |
| `sp_recalc_loyalty_tier` | `RecalcLoyaltyTierJob` | Same logic; tier rules read from the replicated `loyalty_tier_rule` |
| `sp_create_order` + `sp_add_order_item` + `sp_complete_order` | `PlaceOrderJob` | 3 calls / 3 transactions become **1 job / 1 SQL transaction** |
| `sp_score_customers` | `ScoreCustomersJob` | Cursor + 3 queries per customer becomes **three set-based queries** for all customers and one batched upsert |

```bash
cd phase2
./deploy.sh                           # build the jar and deploy it as unit customer360-jobs (a new version each time; callers use "latest")
./run.sh 360 2                        # customer 360 view
./run.sh recalc 2
./run.sh score                        # score every customer (writes customer_score)
./run.sh order 4 APP CARD 4:2,17:1    # customer, channel, payment method, product:qty,...
./run.sh parity all                   # run Sybase procs and GridGain jobs side by side and compare
```

**Parity:** the Sybase harness (`./run.sh parity all`, 16 checks) compares every customer x all 6 result sets of `sp_customer_360`, the tier returned and
stored for every customer, `customer_score` for all active customers, the error numbers for bad input, and a full order. It passed against GridGain
8.9 and again on GridGain 9.2.0-b1 (16 of 16). The Oracle harness (30 checks) also passes on GridGain 9.

**How deployment works:** `deploy.sh` uploads `target/gg-compute.jar` through the REST API as version `1.0.<epoch>` of the unit `customer360-jobs`,
waits for it to be `DEPLOYED` on all nodes and removes the older versions. There is no node restart and no node configuration to change.

**Behavioural differences from the T-SQL (deliberate):**
- `PlaceOrderJob` is all-or-nothing. If item 2 is out of stock, nothing changes; the stored procedures
  left a NEW order with item 1 already decremented.
- Ids for rows created in GridGain come from counter rows in `id_seq` (GridGain 9 has no atomic sequences), starting at 1,000,000,000 so they
  can never collide with Sybase identity values that CDC still replicates.
- `ScoreCustomersJob` reproduces ASE's `datediff(dd, ...)` (calendar-day boundaries, not elapsed 24h) and
  integer `avg()`; those two details are easy to get subtly wrong when porting.

**Before switching Sybase off:** CDC is one-way, Sybase -> GridGain. Rows written by the jobs
(orders, points, stock) exist only in GridGain, so `cdc verify` will show differences once the jobs write,
and a later Sybase change to the same customer would overwrite GridGain's copy. A real cutover therefore
needs the applications to stop writing those entities in Sybase, and GridGain to be the only durable copy (it already has
native persistence). Once that is true, Sybase and the CDC reader are simply decommissioned.
After running `parity order` (which writes to both sides) resync with `cdc/run.sh init` (this drops and
recreates the GridGain tables).

**Other limits:** jobs return maps rather than typed DTOs; job code reads columns by name, so DDL changes need a matching job change.

An airline-style reservations system on Oracle Database 26ai Free, chosen so its data **complements** the Sybase CRM data instead of
duplicating it. Bookings reference the Sybase `customer_id`; there is no foreign key (different system), so only the GridGain hub can join them.


Unlike Sybase, **Oracle runs locally on your Mac** (`gvenzl/oracle-free:23-slim-faststart`, login `travel`/`travel`, service `FREEPDB1`,

### CDC from Oracle (Phase 1)

Same idea as Sybase (row triggers write `(table, op, pk)` to `cdc_change_log`; the reader re-reads the current row and MERGEs it into
GridGain, or DELETEs it), but **the visibility problem is different and so is the fix**. Sybase blocks readers behind uncommitted rows;
Oracle never does, so polling `change_id > last` would silently skip a change whose transaction commits late. The log table is created
with `ROWDEPENDENCIES` so each row carries its own **commit SCN** (`ORA_ROWSCN`); each poll takes a snapshot SCN
(`DBMS_FLASHBACK.GET_SYSTEM_CHANGE_NUMBER`) and reads exactly the rows committed in `(last_scn, snapshot]`. Verified with two sessions:
the one that inserted first but committed later has the higher SCN and lands in a later window instead of being lost.
Applied log rows are purged after 10 minutes (an `ORA_ROWSCN` predicate scans the table, so it must stay small).

```bash
cd cdc
CDC_SOURCE=oracle ./run.sh init      # create the GridGain tables, snapshot, set the SCN offset   (also: run | once | status | verify)
CDC_SOURCE=oracle ./run.sh verify    # every column of every row compared with Oracle
```

GridGain tables (`cdc/src/main/resources/gridgain-schema-oracle.sql`): `booking`, `booking_segment`, `compensation` are partitioned and
**colocated on `customer_id`, exactly like the Sybase customer data** (segments and compensation carry a denormalised `customer_id`);
`airport`, `flight`, `flight_inventory`, `flight_event` are replicated. All TRANSACTIONAL.

### Compute jobs (Phase 2)

| PL/SQL procedure | GridGain job | How it changed |
|---|---|---|
| `sp_customer_trips` | `TripsJob` | one job on the node owning the customer, three queries |
| `sp_book_flight` | `BookFlightJob` | one SQL transaction over inventory, booking and segment |
| `sp_cancel_booking` | `CancelBookingJob` | same rules; the booking's customer is looked up inside the transaction |
| `sp_record_delay`, `sp_cancel_flight` | `RecordDelayJob` | flight + event in one transaction, affected count from a distributed query |
| `sp_process_disruptions` | `ProcessDisruptionsJob` | one set-based query and one batched upsert instead of a cursor |

```bash
cd phase2 && ./deploy.sh                           # deploy the jar as a new version of the unit
./run.sh trips 8 | book 12 2 BUSINESS "A Passenger" | cancel-booking 5 | delay 2 400 weather | disruptions
docker stop gg-cdc-oracle; (cd ../oracle && ./deploy.sh); (cd ../cdc && CDC_SOURCE=oracle ./run.sh init)   # identical starting state
./run.sh parity oracle                             # 30 checks, Oracle procedure vs job on identical inputs
```

**Parity (30 checks):** `sp_customer_trips` for all 204 customers with bookings x 3 result sets; booking (seat, fare, miles, inventory);
full and partial cancellation (refund, statuses, seats released); delay and cancel flight (affected count, status, event text);
disruption processing (summary and the full `compensation` table) and 11 error numbers. Behaviour differences from PL/SQL are deliberate
and few: new ids come from `id_seq` blocks from 1,000,000,000 (never colliding with Oracle identities), and the parity run compares the
test booking each system created apart from its id.

### The hub: joining both systems

Because customer-owned data from **both** sources is colocated on `customer_id`, queries and jobs that join them run on one node with no
data movement. These have no equivalent in either source system:

- **SQL** ([hub/queries.sql](hub/queries.sql), `hub/run.sh` runs them all, or open the file in DBeaver): lifetime value (retail from Sybase + travel
  from Oracle), spend by loyalty tier, **proactive service** (customers with a negative interaction booked on a delayed or cancelled flight),
  top routes for GOLD/PLATINUM customers, a cross-sell list (big retail spenders who never booked a flight), compensation cost by tier. Each runs in a few hundred milliseconds on GridGain 9 (3-30 ms on 8.9: the new engine plans every query and each partition has 3 replicas).
- **`CustomerHubJob`** (`GET /api/v1/customers/{id}/hub`): profile, tier and orders (Sybase) with bookings, miles, upcoming and at-risk trips
  (Oracle), and `lifetime_value = retail spend + travel spend`. Cross-checked against both source databases (e.g. customer 8: 18 orders / 87,550 and
  24 bookings / 66,455 / 174,815 miles).
- **`DisruptionImpactJob`** (`GET /api/v1/flights/{id}/impact`): the passengers of a delayed or cancelled flight, ranked by tier, cabin and retail
  spend, each with the base compensation and a tier-weighted suggested amount (Sybase's loyalty multiplier x Oracle's fare).

## GridGain cluster: 3 nodes, native persistence (GridGain 9.2.0-b1)

```bash
cd gridgain
./cluster.sh up       # start 3 nodes, initialise the cluster once (license), wait until ready
./cluster.sh status   # cluster state and node states
./cluster.sh down     # stop, KEEP data     |     ./cluster.sh wipe   # stop and DELETE the data volumes
```

- The version is one variable, `GG_VERSION` (default `9.2.0-b1`; 9.2.0 final is not published yet, there is no image or Maven artifact for it).
  The compose file builds the node image from `gridgain/Dockerfile`, which takes the **columnar storage jar out of the official image**: on
  Apple Silicon the 9.2.0-b1 arm64 image crashes at node start in that module's native library. Drop the Dockerfile once a fixed image exists.
- Nodes `gridgain1..3` publish the thin-client/JDBC port on host `11800`, `11801`, `11802` and REST on `11300..11302` (shifted by 1000 from the
  defaults so the cluster can run beside another GridGain 9 cluster on the same Mac). All clients list all three, so they fail over. For DBeaver use
  `jdbc:ignite:thin://127.0.0.1:11800,127.0.0.1:11801,127.0.0.1:11802`.
- The cluster is initialised once over REST with the license (`gridgain/gridgain-license.json`, git-ignored; `GG_LICENSE_FILE` overrides the path).
  There is no activation step and no baseline to manage: GridGain 9 starts and rejoins on its own.
- Persistence is the `default` storage profile; every table lives in a distribution zone: `c360` (25 partitions, 3 replicas, so a Raft group
  keeps a majority with one node down) and `c360_ref` (a copy on every node) for the reference tables.
- Node names are fixed by `--node-name node1..3` and discovery lists the three container names.

**Verified (on the 9.2.0-b1 cluster):** with `gridgain3` stopped the API keeps serving reads and jobs, an order is placed with two of three nodes,
the dashboard shows 2 nodes, and the node rejoins with its data.

## REST API (done): `api/`

A separate Spring Boot 3 / Java 17 service that exposes the GridGain data as REST, built into its own Docker
image and deployed on the cluster's Docker network.

```bash
cd gridgain && ./cluster.sh up        # the API joins the cluster's network, so start the cluster first
cd ../api && ./build.sh               # mvn package + docker compose up --build; waits for /actuator/health
./smoke-test.sh                       # 148 end-to-end checks against the running container
./generate-openapi.sh                 # regenerate openapi.yaml from the running service
```

- Swagger UI: http://localhost:8081/swagger-ui.html, spec: [api/openapi.yaml](api/openapi.yaml)
  (OpenAPI 3.0.1, 52 operations, generated from the controllers and DTOs by springdoc, so it cannot drift).
- Base path `/api/v1`. Errors are RFC 7807 problem details; list endpoints return
  `{items, limit, offset, total}`; timestamps are ISO-8601 UTC.

| Tag | Endpoints |
|---|---|
| Customers | `GET/POST /customers`, `GET/PUT/DELETE /customers/{id}` (filters: status, tier, email, q) |
| Addresses | `/customers/{id}/addresses[/{addressId}]` CRUD; one primary address per customer |
| Products | `/products[/{id}]` CRUD; unique SKU |
| Orders | `GET /orders`, `GET/PUT/DELETE /orders/{id}`, **`POST /orders`** = place-order compute job |
| Interactions | `/customers/{id}/interactions[/{id}]` CRUD; closing stamps `closedAt` |
| Loyalty | `GET /loyalty-tiers`, `/customers/{id}/loyalty-transactions`, `/customers/{id}/score` (read-only) |
| Operations | `GET /customers/{id}/360`, `POST /customers/{id}/loyalty/recalculate`, `POST /scoring/run` (compute jobs) |
| Airports | `GET /airports[/{iata}]` (Oracle reference data) |
| Flights | `GET/POST /flights`, `GET/PUT/DELETE /flights/{id}` (with seat inventory), `GET /flights/{id}/events`, `POST /flights/{id}/delay`, `POST /flights/{id}/cancel` |
| Bookings | `GET /bookings`, `GET /bookings/{id}`, **`POST /bookings`** = book-flight job, **`POST /bookings/{id}/cancel`** = cancel-booking job |
| Hub | `GET /customers/{id}/trips`, **`GET /customers/{id}/hub`** and **`GET /flights/{id}/impact`** (join Oracle x Sybase), `POST /disruptions/process`, `GET /compensation` |

**Design notes**
- CRUD runs as SQL over the GridGain thin JDBC driver (all three nodes in the URL, so it fails over).
  The business operations call the Phase 2 compute jobs through the thin client, so stock checks, points and
  tier changes stay atomic and identical to the stored procedures. Job errors keep the stored procedures'
  numbers and map to HTTP: not found (20002, 20103, 20110) -> 404; conflicts (20003 insufficient stock, 20106 flight closed, 20107 sold out,
  20111 not active, 20112, 20121) -> 409; bad input (20004, 20006, 20007, 20104, 20105, 20120) -> 400.
- Bookings, like orders, are only created and cancelled through the jobs (never by raw insert); flights can be created, edited while they have not operated, and
  deleted only when nothing is booked on them.
- Orders are only created through the job (never by raw insert). Order fields are not editable except the
  channel; only CANCELLED orders can be deleted. Customers and products referenced by orders cannot be deleted
  (409): set status INACTIVE or active=false.
- `PUT` replaces all editable fields (omitted optional fields reset to defaults). Loyalty tier and points are
  never writable directly.
- New ids come from counter rows in `id_seq`, in blocks, starting at 1,000,000,000 (no collision with Sybase identities).
- The container runs with `-Duser.timezone=UTC` like the CDC reader and the nodes.

**Limits (PoC):** no authentication; SQL DML is per statement, so cascading customer delete is not atomic;
rows written through the API exist only in GridGain (CDC is one-way), so `cdc verify` shows them as extras
until Sybase is switched off and GridGain is the only copy. `./smoke-test.sh` leaves a few rows behind (including a flight with bookings and compensation rows for the seeded disruptions); `CDC_SOURCE=oracle ./run.sh init` and `./run.sh init` reset GridGain to each source.
Verified: the smoke suite (77 checks at the time, before the travel endpoints) also passed with `gridgain1` (the first address, and coordinator) killed.

### CDC readers as services

Both readers run as containers from one image (`cdc/Dockerfile`, `cdc/docker-compose.yml`), joined to the GridGain network and restarted
automatically: `gg-cdc` (`CDC_SOURCE=sybase`, reaches Sybase by IP `192.168.68.73` because `.local` names do not resolve inside containers)
and `gg-cdc-oracle` (`CDC_SOURCE=oracle`, reaches `oracle:1521`). Never also run `./run.sh run` on the host for the same source.

```bash
cd cdc && ./build.sh        # mvn package + docker compose up --build;   logs: docker logs -f gg-cdc  /  gg-cdc-oracle
```

While streaming, each reader publishes cumulative counters to two small GridGain tables, `cdc_status` (one row per reader: position, backlog,
totals, last-batch size/time/latency; heartbeat every 2 s) and `cdc_table_counts` (row count per source table, every 3 s). The dashboard reads
those. `run.sh init` does not touch them.

### Live dashboard

`http://localhost:8081/` (also `/dashboard.html`) is served by the API container, no external libraries. It shows:

- **Table sizes**: all 17 tables, colour-coded by source system, GridGain rows next to the rows last counted in Sybase or Oracle by the
  CDC reader, with a delta. A positive delta means GridGain holds rows the source does not (rows created through the REST API or compute jobs,
  or the leftovers of `smoke-test.sh`), or the source count is a few seconds behind during a burst.
- **Live graphs** (last 1/5/15 minutes, 2-second samples): CDC events/s, backlog and latency for **Sybase and Oracle side by side**, REST requests/s
  (reads, writes), REST average latency and errors/s. Hover for exact values.
- **Status pills** for GridGain nodes online, each CDC reader running/stopped (heartbeat older than ~10 s = stopped), API uptime.
- A **REST read-traffic generator** (dropdown, runs in the browser) to see the REST graphs move.
  To see the CDC graphs move, change data in Sybase with `sybase/gen-load.sh`:
  `./gen-load.sh 60 100` touches ~100 customer rows/s for 60 s (only `updated_at` changes), and
  `./gen-load.sh --orders 60 5` places ~5 new orders/s through the stored procedures (about 11 CDC events per
  order: orders, items, payment, points ledger, customer, stock). Orders are real Sybase data; `sybase/deploy.sh` resets it.
  `oracle/gen-load.sh 60 5` books ~5 flights/s in Oracle (about 8% cancelled again); `oracle/deploy.sh` resets it.

How it works: the API counts its own business requests in a servlet filter (the dashboard's polling under
`/api/v1/dashboard` is excluded), a scheduled sampler turns those and the CDC counters into per-second rates, and the
data is served by `GET /api/v1/dashboard/summary` and `/series?since=`. CDC rates (per reader) use the reader's publish
timestamps as the time base (using the sampler's clock aliased 65/130 events/s for a steady 100/s). The latency graph
compares a Sybase timestamp with the reader's clock, so it is approximate if the two clocks differ.

## Environment

Oracle runs in the `oracle` container on this Mac (see "Second source" above); GridGain, the API and both CDC readers are Docker containers on the
`gridgain_default` network. The API is published on host port **8081** (`API_PORT` overrides it; 8080 was taken). The GridGain 9.2 client needs
**Java 21**, so the API and reader images use a 21 JRE and the host tools (`run.sh`) need a JDK 21. Sybase is the only remote piece:

## GridGain 9 port (this branch)

This branch moves the project from GridGain 8.9 to **9.2.0-b1**. GridGain 9 is a different product, so most of the GridGain-facing code changed:

| | GridGain 8.9 | GridGain 9 |
|---|---|---|
| tables | caches, `WITH "template=...,affinity_key=..."` | distribution zones, `COLOCATE BY`, `ZONE c360` / `c360_ref` |
| cluster | static XML, activate, baseline | one-off init over REST with the license; no activation |
| jobs | `ComputeTask` map/reduce, BinaryObject cache transactions, jar on each node's classpath + rolling restart | `ComputeJob` deployed as a unit (no restart), SQL transactions, colocated targets |
| ids | atomic sequences | counter rows in `id_seq`, taken in blocks |
| upserts | `MERGE INTO ... VALUES` over JDBC | key-value `RecordView.upsertAll` through the thin client |
| node list | `sys.nodes` | the client's view of the topology |
| reads | consistent | **autocommit reads are a snapshot about 1.5 s old** |

**What was verified:** the Sybase and Oracle CDC readers (snapshot, streaming, verify identical), both parity harnesses (Sybase 16 of 16, Oracle
30 of 30), the API smoke test (148 of 148, run before the Sybase check), the hub SQL, the dashboard, and a node stopped and restarted under load of
requests. The Sybase check ran against ASE on `llama` after the VM was restarted (see "Sybase VM" below); the only fix it needed was an `ORDER BY` in the
parity harness's pre-check query, because GridGain 9 returns rows in a different order from ASE when none is given.

**Behaviour changes to know about:**
- Per-node fan-out is gone: GridGain 9 SQL has no local-only mode, so the scoring and disruption jobs are single set-based jobs.
- Reads outside a transaction are a snapshot about 1.5 s behind (the safe-time propagation plus the allowed clock skew), so a read straight after a
  write by another client can miss it. The jobs and the API repositories therefore read inside read-write transactions, and the parity harness uses
  autocommit-off connections. The dashboard's counters accept the lag.
- Hub queries take a few hundred milliseconds instead of a few milliseconds.
- GridGain 9 JDBC returns `java.time` values for timestamps.
- The 9.2.0-b1 arm64 image needs its columnar module removed (see "GridGain cluster").

## Sybase in Docker: where it runs

ASE runs in a VM on `llama` (kernel 5.4). A plain container works too on any native x86_64 Linux host, including
kernels >= 5.8, with the `LD_PRELOAD` shim in [sybase/docker/](sybase/docker/) (verified on llama, kernel 7.0). It does
**not** run on the Mac: Rosetta and QEMU user-mode both crash it at startup. Root cause, the fix and everything that was
tried are in [sybase/docker/README.md](sybase/docker/README.md).

## ASE gotchas hit so far
- Column order is `type default <x> not null` (default before nullability).
- `raiserror` needs a message number >= 20000 for user errors.
- jTDS: `prepareCall` parses plain T-SQL as a JDBC escape; use `createStatement` for `exec`/`declare` batches.

## GridGain 9 gotchas hit in the port
- DDL cannot run inside a transaction (the API creates `id_seq` at start-up, outside Spring's transactions).
- A job runs in a fresh class loader every time, so nothing can be cached in statics between calls.
- Compute job arguments and results must be a type GridGain can marshal; strings are, so jobs use JSON text.
- `Tuple` column names are the upper-case SQL names (`CUSTOMER_ID`); the colocation key of a colocated call is passed as a `Tuple` too.
- No `__part` hidden column and no local queries; there is no system view of nodes (use the client's `cluster().nodes()`).
- Platform note: ports 10800-10802, 10300-10302 and 8080 were already used on this Mac, hence 11800, 11300 and 8081.

## Oracle gotchas hit so far
- `docker exec` needs `-i` to receive a heredoc; PL/SQL blocks need a `/` terminator (the single-statement helper appends `;`).
- `ROWDEPENDENCIES` on the change log is what makes `ORA_ROWSCN` the real commit SCN; polling by `change_id` would lose late commits.
- ojdbc's `getObject` on a `TIMESTAMP` column returns `oracle.sql.TIMESTAMP`, not `java.sql.Timestamp`: read timestamps with `getTimestamp`.
- GridGain has no `LISTAGG` and its SQL engine cannot do arithmetic on output aliases in `ORDER BY`; use the aggregate expressions.
